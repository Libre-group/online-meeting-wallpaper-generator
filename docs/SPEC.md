## 1. 目的とゴール

### 1.1 何を作るか

会社名・ロゴ・氏名・キャッチコピー・ベース背景画像をフォームに入力すると、Web会議ツール（主に Google Meet、加えて Zoom / Microsoft Teams 等）で「そのまま背景として設定できる画像」が自動生成される、ブラウザ完結型のジェネレーター。

### 1.2 解決したい課題

- 毎回 PowerPoint や Canva でレイアウトを作るのが手間。
- 作っても「会議画面では文字が顔で隠れる」「端が切れる」「小さすぎて読めない」ことが多い。
- 社内で複数人が作ると、見た目がバラバラになりブランドが揃わない。

### 1.3 成功の定義（受け入れ基準）

1. 入力ゼロ（ベース画像のアップロードのみ）でも、そのまま使える画像が出力される。
2. 生成した PNG を Google Meet にアップロードでき、会議中に氏名・会社名が判読できる。
3. ギャラリー表示（小さいタイル）でも主要情報が切れない・隠れない。
4. 入力画像がサーバーに送信されない（後述 3.2）。

## 3. 全体方針

### 3.1 形態

**依存ライブラリなしの単一 HTML ファイル**（HTML + CSS + JavaScript、Canvas API）。

- ファイルをダブルクリックでブラウザが開けば動く。インストール不要。
- 社内配布はファイルをメール添付／共有ドライブ配置で完結。
- 将来 GitHub Pages 等で公開する場合も、同じファイルをそのまま置くだけ。

［推論］法務・士業の現場では「使うためにツールを新規導入する」ハードルが高いため、インストール不要・アカウント不要を最優先にすべきと判断しました。

### 3.2 データの取り扱い（重要）

**アップロードされた画像・入力文字列は一切サーバーに送信せず、ブラウザ内（Canvas / メモリ）だけで処理する。**

- 実装上、`FileReader` でローカル読み込み → `<canvas>` に描画 → `canvas.toBlob()` でダウンロード、という経路のみを使い、`fetch` / `XMLHttpRequest` による外部送信コードを一切含めない。
- これにより、ロゴ画像・氏名・執務室の写真などを外部事業者に渡さずに済む。
- 生成物のダウンロードはブラウザのローカル保存機能を使用。

［推論］秘密保持の観点から、オンライン画像加工サービスを使わずに内製する価値の中心はここにあると考えます。仕様として明文化しておきます。

**すべてヒアリングで採用が確定（§12.1）。**

#### F-10 QRコードの実装方針

外部通信を行わない方針（§3.2）のため、QRコード生成ライブラリを CDN から読み込まず、
**JIS X 0510 / ISO/IEC 18004 に基づくエンコーダーを自前で実装**して `index.html` に同梱する。

- 対応: バイトモード（UTF-8）、型番1〜15、誤り訂正レベル L / M / Q / H
- 検証: ①符号語・データ配置・形式情報を Python の segno と突き合わせて一致を確認、
  ②OpenCV の QRCodeDetector で 84 件すべて読み取り成功、
  ③ブロック構成表を行列の幾何から独立算出して全型番で整合を確認（`tests/qr.test.mjs`）

### 4.2 出力設定

| # | 項目 | 選択肢 | 既定値 |
|---|---|---|---|
| G-01 | 出力サイズプリセット | §6 の表から選択 | Google Meet 1920×1080 |
| G-02 | ファイル形式 | PNG / JPEG | PNG |
| G-03 | JPEG 品質 | 60–100% | 85%（JPEG選択時のみ） |
| G-04 | ファイル名 | 自動生成（例: `bg_meet_1920x1080_山田.png`） | 自動 |

#### F-01 ベース背景画像の縦横比（v1.1 で改善）

出力は 16:9 のため、16:9 でない画像を「全面に広げる（cover）」で貼ると端が切り取られる。
切り取られる割合は ［計算］ で確定する。

| 読み込んだ画像 | 例 | cover で切り取られる割合 |
|---|---|---|
| 4:3 | 1600×1200 | 上下あわせて 25% |
| 3:2 | 1500×1000 | 上下あわせて 11% |
| 縦長 9:16 | 900×1600 | 上下あわせて 68% |

**対応**:
1. 画像を読み込んだ時点で切り取り率を計算し、**8% を超える場合は自動的に
   「画像全体を入れる（contain）」へ切り替え**、切り取り率を明示して知らせる。
2. contain で生じる余白は、**同じ画像を拡大してぼかしたもので埋める**（既定ON）。
   単色の帯より自然で、情報量も損なわれない。
3. ズームの下限を 100% から **25%** に下げ、縮小もできるようにする。
4. 「画像全体を入れる」「全面に広げる」のワンクリック切替を用意する。
5. 画像を入れ替えたら、その画像に合った既定（切り取り率で判定）から始める。

#### F-02 会社名・事務所名の複数行表示（v1.2）

グループ名と所属法人を併記する用途のため、改行で **最大4行** まで入力できる。

- 入力欄は複数行（textarea）。改行がそのまま行の区切りになる。
- 1行が長い場合は、レイアウトごとに決めた幅で自動的に折り返す
  （A・B: 画像幅の40%、C: 26%、D: 34%）。
- 行送りは文字サイズの 1.3 倍（キャッチコピーの 1.45 倍より詰める）。
- 5行以上入力された場合は先頭4行のみ表示し、入力欄の下に注意書きを出す。

#### F-11 マスコット画像（v1.3）

ロゴとは別に、キャラクター画像を1枚、文字の並びとは独立して配置できる。

| 項目 | 内容 |
|---|---|
| 大きさ | 画像高さの 5〜60%（既定 28%） |
| 置き場所 | 左下（既定）／右下／左上／右上。ワンクリックで切替 |
| 左右反転 | あり。画面の外を向いているキャラを内側に向かせるため |
| 微調整 | ドラッグ、および「6. 微調整」で位置・大きさを調整できる |

置き場所は §8 のセーフゾーンに従い、「配置の優先度」で指定した余白の内側に収める。
既定を左下にしているのは、主情報（レイアウトA・B・C・E）が右側にあり衝突しないため。

### 4.3 レイアウト機能

- **L-01 レイアウトプリセット**: §7 のプリセットから1クリックで選択。位置・サイズ・文字揃えが一括で決まる。
- **L-02 置き場所と微調整（v1.4 で刷新）**: ブロック（主情報・副情報・キャッチコピー・QR・マスコット）ごとに、
  - **置き場所を9か所から選べる**（左上／上／右上／左／中央／右／左下／下／右下）。
    行（上・中・下）で**基準点と伸びる向き**が、列（左・中・右）で横の基準が決まる。
    「下」を選べば下端から上に積み上がるため、下に寄せても画像からはみ出さない。
  - 「レイアウトの既定位置に戻す」でレイアウト本来の位置に戻せる
  - 微調整（X / Y）は **±100%**（v1.3 までは ±40%）。ドラッグも同じ範囲
  - 大きさ（画像高さに対する％で指定 → どの出力サイズでも見た目が一定になる）
  - 動かしすぎても消えないよう、ブロックの**2割以上は必ず画面内に残す**
  - プレビューでは選択中のブロックを青い点線で示す（書き出した画像には入らない）
- **L-03 リセット**: プリセットの既定値に戻す。
- **L-04 背景の加工**:
  - ベース画像のフィット方式（cover / contain / 手動ズーム・位置）
  - 明度オーバーレイ（黒 or 白を 0〜70%）: 写真の上でも文字を読ませるための必須機能
  - ぼかし（0〜20px）
  - 文字の下に敷く「読みやすさパネル」（半透明の矩形帯）の ON/OFF

#### 色の指定（v1.4 で刷新）

v1.3 までは、背景画像を入れると背景色の指定が一切効かず（画像の下に隠れるため）、
文字の下のパネル・レイアウトCの帯・Dのバーはすべて黒の固定値だった。

| 設定 | 内容 | v1.3 まで |
|---|---|---|
| 重ねる色 | 背景の上に重ねる色と不透明度（0〜70%）。写真全体をブランドカラーで染められる | 黒のみ（「暗くする」） |
| パネル・帯の色 | 文字の下のパネル、レイアウトCの帯、Dのバーに共通で使う色と不透明度 | 黒 38% 固定 |
| 配色プリセット | ダーク（既定）／ライト／ブランド色 をワンクリック切替 | なし |

- 文字の影は**文字色の明るさに応じて自動で切り替える**（明るい文字には暗い影、
  暗い文字には明るい影）。これによりライトの配色でも文字が沈まない。
- QRコードの下地だけは白のまま固定する。読み取りには明地に暗モジュールが必要なため。
- 既定のパネルは **#101820 / 50%**（v1.3 までは黒 38%）。文字のコントラストを上げるため
  わずかに濃くした。

［推論］L-04 の明度オーバーレイは「見た目の好み」ではなく**可読性の担保手段**です。写真をそのまま使うと文字が必ず読みにくくなるため、既定 ON（黒15%程度）を推奨します。

#### 文字の読みやすさ（v1.5）

##### 背景に埋もれる文字への対策

v1.4 までの問題［実測］: 配布用テンプレート（白・黄色の背景）では、パネルのないキャッチコピーの
下地が完全な白で、白文字とのコントラスト比は **1.00:1**（同じ色）だった。文字色は全体で1色のため、
文字色を濃くすると、今度はパネル上の社名・氏名が読めなくなる。この問題はキャッチコピーに限らず、
**パネルのないブロックすべて**（レイアウトC・D・Eの主情報など）に起こる。

対策は全ブロック共通の仕組みとして実装する。

| 機能 | 内容 |
|---|---|
| 文字色の自動調整（既定ON） | ブロックごとに、文字を置く範囲の背景を描画済みの画像から読み取り、WCAG 2.x の相対輝度でコントラスト比を計算する。評価は**読みにくい側の1割**（10パーセンタイル）で行う（平均だと明暗の混ざった背景を見逃すため） |
| ├ パネルのあるブロック | まず**パネルを濃くして**文字色を保つ（デザインの意図を崩さないため）。4.5:1 に届くまで濃さを最大 90% まで 4% 刻みで上げる |
| ├ パネルのないブロック | 文字色のままでは 4.5:1 に届かない場合だけ、白（#ffffff）か濃紺（#16202b）のうち比が高い方に切り替える |
| └ アクセント色 | 資格名などのアクセント色は、大きい文字の基準 3:1 を下回るときは文字色に合わせる |
| 縁取り | なし（既定）／細（文字の大きさの 9%）／太（18%）。文字色と反対の明るさの色で縁を描く。明暗が混ざる写真背景向け |
| ブロックごとのパネル | 主情報・副情報・キャッチコピー・QR ごとに「レイアウトの既定に従う／敷く／敷かない」を選べる |

- 影の色も、実際に使う文字色の明るさに合わせて切り替える。
- 基準値（通常の文字 4.5:1、大きい文字 3:1）は WCAG 2.x のコントラスト基準による。

効果［実測・配布用テンプレート］:

| 箇所 | 自動調整なし | 自動調整あり |
|---|---|---|
| キャッチコピー（パネルなし、白背景） | 2.24:1 | **12.49:1**（濃紺文字に切替） |
| 名刺パネル（濃紺50%を白背景に重ねた灰色）と白文字 | 3.43:1 | **5.00:1**（パネルを濃くし、白文字は維持） |

※ 前者は描かれた文字の画素と背景の比の中央値、後者はパネル地と白の比。

##### 補助情報の文字が小さい問題への対策

v1.4 までの問題［計算］: ふりがな・連絡先は画像の高さの 2.0%、資格・肩書は 2.4% だった。
1080p の画面に 2×2 で並べると（タイルの高さ約540pxと仮定）、ふりがなは**約11px**になる。
約12px 未満は読みにくいとの目安［推論］を下回る。

| 文字の大きさ | 補助情報（ふりがな・肩書・資格・連絡先） | その他 | 2×2表示 | 3×3表示 |
|---|---|---|---|---|
| 標準 | レイアウトの既定（2.0〜2.4%）・細字 | 変更なし | 約11px | 約7px |
| **大きめ（既定）** | 3.0% 以上・太字（600） | 変更なし | 約16px | 約11px |
| 特大 | 3.4% 以上・太字（600） | 社名・キャッチコピーも 3.4% 以上 | 約18px | 約12px |

- 「大きめ」「特大」は下限を設けるもので、レイアウトの既定がそれより大きい場合はそのまま使う。
- 「標準」は v1.4 までと同じ見た目（大きさ・太さとも）。

##### 読みにくさの注意

プレビューの下に、描画した文字の大きさから見積もった注意を出す。

| 種類 | 条件（1080p の画面での目安） | 表示 |
|---|---|---|
| 強い注意 | 2×2 表示で 12px 未満 | 該当要素名とおおよその大きさ、直し方 |
| 控えめな注意 | 3×3 表示で 12px 未満 | 大人数の会議では「特大」を勧める |

タイルの大きさは画面サイズ・参加人数・ツールで変わるため、表示は目安である旨を併記する。

### 4.5 保存・再利用

- S-01: 入力内容（画像を除くテキスト・座標・色）を JSON としてエクスポート／インポート。
- S-02: 入力内容を `localStorage` に自動保存し、次回開いたときに復元。
  背景画像は容量が大きく `localStorage`（上限 約5MB）に入らないため、**`IndexedDB` に別途保存**する（v1.6）。

#### S-02 補足: 背景画像が反映されない問題（v1.6 で修正）

v1.5 までは背景画像を保存していなかったため、既定テンプレート入りの配布用ファイルでは、
自分で入れた背景が**開き直すと会社の既定の背景に戻っていた**。利用者からは
「背景を入れても反応しない（反映されない）」ように見える。あわせて以下も対応した。

| 症状 | 原因 | 対応 |
|---|---|---|
| 開き直すと既定の背景に戻る | 背景画像を保存していなかった | `IndexedDB` に保存し、開いたときに復元する。「画像を外す」も保存する |
| 同じファイルを選び直しても反応しない | ブラウザは前回と同じファイルが選ばれると変更通知を出さない | ファイル選択を開く前に選択状態を空にする（背景・ロゴ・マスコット） |
| iPhone の写真が読み込めない | HEIC 形式は多くのブラウザで表示できない | 理由と対処（JPEG/PNG に変換）を背景欄に表示する |
| 予期しないエラーで止まると何も起きないように見える | エラーが画面に出なかった | プレビューの上にエラー内容を表示する |

復元の規則: 保存時の既定テンプレートの版（書き出し日時）を一緒に記録し、版が同じときだけ復元する。
管理者が既定テンプレートを更新した場合は、会社の新しい背景を優先する（他の会社設定と同じ扱い）。

再現できなかった事項［事実］: 作業環境（ヘッドレスの Chromium）では、背景画像を選んだ直後に
プレビューが変わらない現象は再現しなかった（通常の写真・4032×3024 の写真・旧版の保存データからの移行・
CPU を 1/4 に落とした状態のいずれも）。上記の修正後も起きる場合は、ブラウザの種類・画像の形式・
手順・画面に出たエラー表示の確認が必要。
- S-03: 「会社テンプレート」として、ロゴ・会社名・色・レイアウトのみを固定し、氏名だけ差し替えるモード。
- **S-04: 既定テンプレートの HTML 埋め込み（v1.1）**。詳細は §4.6。

［推論］S-03 は、社内全員分を同じデザインで量産する運用に直結するため、優先度を高く置くことを提案します。

### 4.6 既定テンプレートの埋め込み（S-04）

「開いた時点で会社の設定が入っている」状態を、サーバー側の仕組みなしで実現する。

**仕組み**

`index.html` 内に次の枠を持たせ、ここにテンプレートJSONを埋め込む。

```html
<script type="application/json" id="embedded-template">null</script>
```

「この設定を既定にしたHTMLを書き出す」ボタンは、**表示中のページのDOMを複製し、
この枠だけを差し替えて新しい `index.html` を書き出す**。外部通信は行わない
（`fetch` でページ自身を読みにいく方式は採らない）。

- 実行時に JavaScript が生成した要素（背景色プリセット）は複製から取り除く
- 埋め込むJSONは `<` を `\u003c` にエスケープし、スクリプトの終了タグとして
  解釈されないようにする
- 氏名・ふりがな・肩書・資格名・連絡先・QRは **埋め込まない**（個人情報）
- **背景画像・ロゴ・マスコット画像は常に埋め込む**。「既定の設定」として使う以上、
  画像が欠けていては意味がないため、チェックボックスの状態に依存させない
  （チェックボックスはJSONテンプレート書き出し専用）
- 背景画像のデータが 1.5MB を超える場合は、**JPEG・最大2560px に再圧縮**してから
  埋め込み、その旨を画面に表示する。ロゴとマスコットは透過を保つため再圧縮しない

**読み込みの優先順位**

| 状況 | 動作 |
|---|---|
| 初回（この端末に保存なし）＋埋め込みあり | 埋め込みを適用し、「氏名の差し替えのみ」モードで開く |
| 2回目以降（保存あり）＋埋め込みが同じ版 | **埋め込みを土台に、端末の保存内容を上から重ねる**。自分で入れた背景画像は `IndexedDB` から復元する（v1.6） |
| 2回目以降＋**埋め込みが更新されている** | 氏名などは端末のものを残し、会社の設定だけ新しい版に入れ替える |
| 埋め込みなし | 従来どおり（サンプル値で開く） |

版の判定は、書き出し時刻（`_stamp`）を埋め込みJSONと端末の保存の双方に持たせて比較する。
これにより、管理者が共有先のファイルを更新すれば、利用者の画面にも自動で反映される。

**テンプレート編集機能は維持する。** 埋め込み版でも「テンプレート編集」モードに
切り替えれば全項目を編集でき、再度書き出して置き換えられる。
「既定テンプレートに戻す」ボタンで、氏名を保ったまま会社の設定だけ戻せる。

## 5. 非機能要件

| 区分 | 要件 |
|---|---|
| 対応ブラウザ | Chrome / Edge 最新版を主対象。Safari / Firefox 最新版も動作させる |
| 実行環境 | PC（デスクトップ）。スマホ対応は必須としない |
| 外部通信 | なし（CDN・Webフォントも含めて外部読み込みを行わない） |
| 依存ライブラリ | なし（素の Canvas 2D API のみ） |
| ファイル構成 | `index.html` 単一（CSS / JS をインライン）。保守性を優先する場合は分割も可 |
| 生成速度 | 入力変更からプレビュー反映まで概ね即時（数百ms以内） |
| アクセシビリティ | フォーム項目に `<label>` を紐付け、キーボード操作可能にする |

### 5.1 フォントの扱い（注意点）

Canvas で描画する文字は **閲覧者の PC にインストールされたフォント**を使用します。Webフォントを外部から読み込まない方針（5. 外部通信なし）のため、指定できるのは OS 標準フォントに限られます。

- Windows: 游ゴシック、メイリオ、BIZ UDPゴシック 等
- macOS: ヒラギノ角ゴシック 等
- CSS のフォントファミリー指定でフォールバックを並べ、環境差を吸収する。

［推論］ブランドフォントを厳密に使いたい場合は、フォントファイル（.woff2）を同梱してローカル読み込みする方式に変更が必要です。ただしフォントのライセンス上、再配布や埋め込みが許諾されているかの確認が別途必要になります（§11）。

## 6. 出力サイズプリセット

### 6.1 結論（実務上の要点）

**主要ツール間でサイズ要件に大きな違いはありません。いずれも 16:9 / 1920×1080 が推奨です。** ツールごとに実質的に異なるのは「対応ファイル形式」「ファイルサイズ上限」であり、レイアウト設計で本当に効いてくるのは §8 のセーフゾーンの方です。

### 6.2 プリセット表

| プリセット | 解像度 | 比率 | 用途・根拠 |
|---|---|---|---|
| Google Meet（既定） | 1920×1080 | 16:9 | ［二次情報／要確認］最低 1280×720、推奨 1920×1080、16:9 |
| Zoom | 1920×1080 | 16:9 | ［二次情報／要確認］推奨 1920×1080、16:9 |
| Microsoft Teams | 1920×1080 | 16:9 | ［二次情報／要確認］推奨 1920×1080 |
| 汎用・高解像度 | 2560×1440 | 16:9 | 大型ディスプレイ・画面共有時の劣化対策 |
| 汎用・4K | 3840×2160 | 16:9 | ファイルサイズ上限に注意 |
| 軽量 | 1280×720 | 16:9 | ファイルサイズ上限が厳しい場合の保険 |

### 6.3 ファイル形式・容量（要確認事項）

| ツール | 対応形式 | ファイルサイズ上限 |
|---|---|---|
| Google Meet | ［二次情報／要確認］JPG / PNG / GIF。「JPG・sRGB・16MB未満」とする記述もあり、情報が一致していない | ［要確認］16MB との記述あり |
| Zoom | ［二次情報／要確認］GIF / JPG / 24bit PNG（アルファなし） | ［要確認］5MB とする記述と 15MB とする記述が混在 |

**対応方針**: 情報が確定するまでは、
1. 既定を **PNG / 1920×1080** とする（実測で概ね数MB以内に収まる）。
2. 生成後に**推定ファイルサイズを画面に表示**し、5MB を超えた場合は「JPEG への切り替え」を促す警告を出す。
3. JPEG 出力時は sRGB・アルファなしで書き出す（Zoom の 24bit PNG 要件・Meet の sRGB 要件の双方を満たす安全側の設定）。

［推論］上限値の一次情報が確定していない以上、「上限を守る」より「どのツールでも確実に通る安全側（5MB以内・JPEG可）を選べるようにする」設計が実務的です。公式ヘルプでの確認後、数値を本仕様書に反映します。

## 7. レイアウトプリセット

すべての座標は**画像幅・高さに対する比率（％）**で定義する。これにより、1280×720 でも 3840×2160 でも同じ見た目になる。

**ヒアリング結果により、A〜E すべてを画面上から任意に選択できる方式で実装した。** 既定は A。

| ID | 名称 | 配置の考え方 | 向いている用途 |
|---|---|---|---|
| **A** | 右下・名刺型（**既定**） | ロゴ＋会社名＋氏名＋肩書を右下ブロックに右揃えで配置 | 汎用。最も事故が少ない |
| **B** | 左上・ヘッダー型 | ロゴ＋会社名を左上、氏名を右下に分離 | ブランド訴求 |
| **C** | 右サイド帯型 | 画面右 30% に半透明の縦帯を敷き、その中に全情報を縦積み | 情報量が多い場合 |
| **D** | 上部バー型 | 画面上端に横帯。会社名を左、氏名を右 | キャッチコピーが長い場合 |
| **E** | ミニマル型 | 氏名のみを右下に小さく | 社内会議・写真を見せたい場合 |

### 7.1 既定プリセット A の定義（案）

| 要素 | X（右端基準） | Y（下端基準） | サイズ（画像高さ比） |
|---|---|---|---|
| ロゴ | 右から 6% | 下から 26% | 高さ 8% |
| 会社名 | 右から 6% | 下から 20% | 3.0% |
| 氏名 | 右から 6% | 下から 12% | 6.5% |
| 肩書 | 右から 6% | 下から 7% | 2.6% |
| キャッチコピー | 左から 6% | 上から 10% | 3.2% |

［推論］この数値は §8 のセーフゾーン計算に基づく初期案です。実際に Meet で表示して微調整することを前提としています。

## 8. セーフゾーン設計（本ジェネレーターの中核）

「きれいに作ったのに会議では読めない」を防ぐための設計根拠です。

### 8.1 タイル表示によるトリミング ［計算］

Web会議のギャラリー表示では、参加者のタイルは 16:9 とは限りません。1920×1080 の背景が中央基準で切り出される場合、**幾何学的に確実に**次のようになります。

| タイルの比率 | 残る幅 | 左右で切れる幅（片側） |
|---|---|---|
| 16:9 | 1920px（100%） | 0px |
| 4:3 | 1440px（75%） | 240px（12.5%） |
| 1:1（正方形） | 1080px（56.25%） | 420px（21.875%） |

**結論**: 正方形タイルでも必ず残るのは、**左右から 21.9% を除いた中央 56.25% の帯**だけです。

### 8.2 人物が隠す領域 ［推論］

一般的な着座のバストアップ構図では、画面中央のおよそ **幅 35〜45%・下半分**を人物が占めます。ここに文字を置くと隠れます。

### 8.3 ツール UI が重なる領域 ［推論／要実機確認］

Google Meet・Zoom ともに、タイルの**左下**に参加者名が表示されます。ここに氏名を置くと二重表示になり、かつ重なります。

### 8.4 以上から導かれる推奨配置ゾーン

上記3条件を重ねると、**主要情報（氏名・会社名）を置くべきなのは次の帯**になります。

- **推奨ゾーン（右）**: X が **62%〜78%** の範囲
- **推奨ゾーン（左）**: X が **22%〜38%** の範囲（ただし左下は UI と競合するため上寄せ）

（＝「1:1 トリミングでも残り」かつ「人物に被らない」領域）

- **絶対に避ける**: 左右端 各 22%（切れる）、中央 40%（人物）、左下隅（UI）
- **装飾のみ可**: 左右端 22% の領域。切れても支障のないグラデーション・模様に限定する。

プレビュー機能 P-02 では、この3種類のゾーンを色分けして重ね表示する。

## 9. 左右反転（ミラー）の扱い

［二次情報／要確認］Google Meet・Zoom とも、**自分の画面に映る自分の映像は既定で左右反転**しています。背景に入れた文字は、**自分には裏返しに見えるが、相手には正しく見える**というのが既知の挙動です（Zoom には「マイビデオをミラーリング」設定があり、これを切ると自分の画面でも正しい向きで表示されます）。

**対応方針**:
- 生成画像そのものは**反転させない**（相手に正しく見えるのが正）。
- プレビューに「自分の画面での見え方（左右反転）」トグル（P-05）を用意し、**「文字が裏返って見えるのは正常です」という説明文を常設**する。
- 実機で挙動を確認のうえ、説明文を確定する。

［推論］この点は問い合わせが集中するポイントなので、UI 上に注記を常時表示しておく価値が高いと考えます。

## 11. 法務・権利上の留意点（利用上の注意として画面に明記）

［推論］本ツールは画像を生成するだけで、生成物の利用可否までは保証しません。UI 上に以下の注意書きを常設することを提案します。

1. **ベース画像**: フリー素材を使う場合、商用利用可否・改変可否・クレジット表記要否をライセンスで確認すること。
2. **ロゴ**: 自社ロゴであっても、ロゴ使用規程（余白・改変禁止等）がある場合はそれに従うこと。
3. **執務室の写真**: 書類・モニター・第三者が写り込んでいないか確認すること（守秘義務・個人情報の観点）。
4. **フォント**: 本ツールは端末にインストール済みのフォントを利用します。生成画像の商用利用可否は、当該フォントのライセンスに従います。
5. **他社ロゴ・商標**: 無断使用は商標権・不正競争防止法上の問題となり得ます。
